# cleat-105 量化后决定：封闭局部 fn 提升、闭包直接 Invoke、内联预算

- 里程碑：M10　依赖：cleat-104　状态：完成（2026-10-15，量化后不实现，见结果）
- 设计依据：[20 §6](../designs/20-skeg-optimizations.md)；skeg iron-085 / 070

## 工作内容
1. 用 cleat-100 的工具量化：局部 fn 的分配与调用开销、`.inl` 内联预算放宽的收益。
2. 值得的部分实现：封闭的局部 fn 提升为静态单例 / 已知函数；闭包的子句方法直接作为 `invoke` 覆盖；内联预算调整。
3. 不值得的记录数字后关闭任务。

## 验收标准
- 每项有基准前后数字；基线、门禁、全量不变。

## 结果（2026-10-15，linux01，Release，cleat-104 之后）

### 测量（5M 次调用，函数体 `(* x 2)` 一类，循环 `(+ s (g i))`；分配为 GC.GetTotalAllocatedBytes 之差；第 3 ~ 4 轮）
| 写法 | 耗时 | 分配 | 说明 |
|---|---|---|---|
| 循环里的封闭 lambda `((fn [x] (* x 2)) i)`（每轮 newobj） | 83 ms | 360 MB | 与 let 里建一次相同：闭包对象不逃逸，JIT 消化掉 |
| let 绑定的封闭 lambda `(g i)` | 79 ~ 83 | 360 | callvirt IFn.invoke → invokeStatic |
| 捕获局部的闭包 | 82 | 360 | |
| 循环里捕获局部的闭包（每轮 newobj 带字段） | 92 ~ 96 | 520 | 每轮多 32 字节，JIT 未消化 |
| 同一 lambda 带 `^long` 提示、`.invokePrim` 调用 | 24 ~ 25 | 0 | 不装箱 |
| 顶层 `(dbl i)` 经 Var | 93 | 360 | |
| 顶层 `^long` 提示的 `(pdbl i)`（PrimInvoke） | 22 | 0 | |
| 同样的运算直接写在循环里 | 1 ms / 1M | 0 | |
| `.inl` 内联开关（`CLEAT_NO_OPT=inline`） | 不变 | 不变 | 同一单元的用户函数不经 `.inl`；只影响包与镜像里的函数 |

每次调用 72 字节 = 实参、返回值与累加结果三次 Long 装箱。经装箱的调用每次 16 ~ 19 ns，不装箱的 4.5 ns。

### 决定
1. 封闭局部 fn 提升为静态单例：不做——稳态没有差别（第一轮未热身时 144 对 84 ms，之后相同）。只有"循环里每轮新建、带捕获字段"的闭包多分配，实际代码里少见。
2. 闭包的子句方法直接作为 `invoke`：不做——虚调用与转发占每次调用的一小部分，开销在装箱（不装箱的 invokePrim 快 3.5 倍，分配为 0）。
3. 内联预算：不适用——同单元用户函数不内联，镜像函数的内联与本测量无关。
4. 真正的开销是跨函数边界的装箱。对应的优化是"类型已知的调用点直调"（cleat-104 工作内容第 2 项中没做的部分）：
   非递归的纯数值函数也有类型化入口，调用点实参类型已知时直调 invokeStaticTyped（Var 的值不是该类时走通用调用，结果用 Num 承接，不需要退回）；
   let 绑定、不被赋值的已知 lambda 连 Var 检查都不需要。记为候选（designs/20 §6），优先级由 cleat-107 的 r7rs 对比决定。
