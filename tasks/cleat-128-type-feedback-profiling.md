# cleat-128 类型反馈：剖面记录、触发与量化

- 里程碑：M13　依赖：cleat-119　状态：完成（2026-10-17）
- 设计依据：[23 §2.1](../designs/23-type-specialization.md)

## 工作内容
1. 候选：满足 cleat-104 类型化入口条件、但编译期推测不成立或没有推测的 eval 函数。
2. 通用入口按形参记录方法表指针与计数（函数类的静态字段，不分配；看到第二种类型标为多态；达到阈值后停止记录）。
3. 触发条件：调用计数或循环回边计数到阈值且各形参单态 → 记为特化候选（本任务只记录，不特化）。
4. 量化：记录对调用密集函数（fib、tak 一类）的开销；r7rs 与 bench/ 里会被触发的函数数量与形参类型分布；开关 `CLEAT_NO_OPT=typefeedback`。

## 验收标准
- 记录开销与触发统计写进任务书；据此决定 cleat-129 是否开工（收益上界不足时关闭 129 并记录）。
- 开 / 关输出逐字相同；基线、门禁、全量不变。

## 实现记录（2026-10-17）

- 候选选择挂在 cleat-104 的类型化入口之后：eval 单元、无自由变量、单固定子句、1 ~ 4 个 object 形参、体满足纯运算条件；
  编译期类型化入口成立时继续走 TypedEntry，不重复记录；成立不了时登记函数类与 arity。
- 函数类保存 `tfName` / `tfOn` / 每形参计数、类型槽与诊断名。`invokeStatic` 先读一次 `tfOn`，活动时把实参传给同类独立的
  `ProfileArgs` 方法；达到阈值时 `TypeFeedback.Profile` 返回 false 并写回 `tfOn`，之后不再进入记录路径。独立小方法隔离了
  直接调用剖面运行时与入口后续分支组合时 RyuJIT 报 `InvalidProgramException` 的形状。
- 类型槽直接保存 CLR `Type` 实例（null 与多态各有哨兵），第一类触发前用引用比较判断单态；1 ~ 4 个形参都有独立重载，
  记录路径不分配实参数组。`Snapshot` / `Summary` 输出调用数、每参数类型、单态触发与多态分布。
- 语义测试覆盖 1 / 2 / 3 / 4 元单态触发、同一形参 `Int64 → String` 变多态后不触发，以及 `CLEAT_NO_OPT=typefeedback`
  开 / 关的逐字输出。

### 量化与 129 决定

- 本机调用密集微基准（一个两参候选函数，50,000,000 次直接调用，5 次交替）：开启 184 / 186 / 187 / 189 / 192 ms，
  关闭 151 / 151 / 150 / 151 / 152 ms；中位数 187 → 151 ms，稳态残差 36 ms（约 23.8%，0.72 ns / 次）。
  前 1000 次的类型记录本身被长跑摊薄，残差主要来自关闭后的静态布尔分支。
- 标准 `bench/`（14 项常规文件执行）全部 `reports=0 triggered=0 profiled-calls=0`：文件 / 镜像路径不是 eval 单元，
  且既有类型化入口或内联已覆盖这些热点；r7rs 的常规 `-I … -m …` 文件执行同样不走本机制（抽样 sum / fib / tak / mazefun
  均为 0）。
- 结论：现有 r7rs / bench 目标没有可特化的受益函数；仅为了通用 eval 代码引入 cleat-129 的后台重编译、安装与失效机制
  收益上界不足。**cleat-129 关闭**，保留 cleat-128 的诊断剖面与开关，待出现真实 eval 热点负载后再重新量化。
