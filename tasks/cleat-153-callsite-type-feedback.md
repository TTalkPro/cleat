# cleat-153 调用点的运行时类型反馈（接口调用单态化）

- 里程碑：M17　依赖：cleat-145（访问器内联，同一套"具体类型守卫 + 直读 / 直存"发射）　状态：未开始
- 设计依据：[27](../designs/27-jit-style-runtime-specialization.md)、[28 §2.3 / §3](../designs/28-hot-path-optimizations.md)、
  [notes 的 M15 差异归因 §1](../notes/r7rs-performance.md)

## 问题

145 把"小访问器的 defn 包装"消掉之后，pair 密集项剩下的成本是**接口调用点本身**。M15 归因的微基准表（111，ns/次）：

| 形状 | cleat | JVM C2 |
|---|---:|---:|
| mcar 读（包装 + 接口调用） | 2.9 | 1.3 |
| mcdr 读 | 4.4 | 1.0 |
| 可变字段写 + 读 | 14.1 | 4.8 |

28 §2.3 复核后的结论是"defn 包装比接口直调贵约 2 ns（3.4 vs 1.3）"，145 处理的是这 2 ns；
**没被处理的是那 1.3 ns 从哪来**：JVM 侧 C2 在调用点上按运行时类型画像做去虚化（单态时一条守卫 + 直接调用，
多态时才走 vtable），而 cleat 的 `CallInstance` 在只知接口类型时永远是接口分派 + 装箱实参。
`browse / scheme / peval / destruc / nboyer` 这些 pair 密集项每轮迭代都要付这笔钱。

cleat 这一层的基建已经在 M14 / M15 建好但只用在**函数入口**上：132 ~ 138 的按参数类型特化、
RuntimeSigEntry 签名表、139 的整体函数特化、140 的编译期调用路径类型推导（[27](../designs/27-jit-style-runtime-specialization.md)）。
**缺的是把同一套观察 / 特化机制用到"接口调用点"上**：观察该点的实际接收者类型分布，单态时把调用点重编成
具体类型守卫 + 字段直读 / 直调（与 145 的守卫同形），守卫失败退回原来的接口调用。

## 工作内容

1. **先量化，不动代码**：`bench/r7rs/src/micro.cljc` 补三格对照 —— 同一 deftype 上"接口直调 / 提示为具体类型的
   直调 / 经 145 内联后的字段直读"，并加一格"同一调用点两种类型交替"（多态代价）。
   探针结果必须参与数据依赖（149 §1 的口径），否则 JVM 侧被 C2 消掉，量不到真东西。
2. **观察点**：接口调用点的接收者类型计数放哪儿 —— 优先复用 RuntimeSigTable / 签名 key 的现有表（135 / 136 / 138），
   不新建第二套反馈设施；确认计数与查表的**每次调用成本**不高于它省下的分派成本（这条不成立就停手，按 28 §3 的纪律记账）。
3. **特化发射**：单态达标后为该调用点生成"类型守卫 + 直调 / 直读"的版本，守卫失败回落到通用 `CallInstance`；
   与 145 共用 codegen 的守卫形态，避免两套 stfld / ldfld 发射。
4. **开关**：并入既有的 `CLEAT_NO_OPT=typefeedback`（149 §3 矩阵里已在册的开关），**不新增缺省行为**；
   矩阵里 > 2x 的格子只证明退化路径不能被整体关掉，不用于反推收益。
5. **不能回退的两条既有结论**：cleat-120 的 array1 循环内联限制（tier-0 形参活性）与 28 §6 的分支位置纪律
   —— 反馈守卫不得进循环体热路径的分支链头部，A/B 名单必须含不受利的列表 / 序列密集项。

## 验收

  本任务收口为"量化 + 记账"）。

  三类，开 / 关输出逐字相同；语料门禁 gate 521、CTS 6868/29/6、test-clojure 基线逐字一致。
